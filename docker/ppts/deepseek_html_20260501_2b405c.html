🔑 Key Takeaways from the Course

  • Containers share the host OS kernel — no guest OS needed → faster than VMs
  • Namespaces = isolation (PID, Network, Mount, UTS, User)
  • cgroups = resource control (CPU, Memory, Disk I/O limits)
  • Images are immutable and built in layers (cached for speed)
  • Registries (Docker Hub, ECR, ACR) store & distribute images
  • docker run -d -p 8080:80 --name myapp nginx — the most common pattern

🏠 Virtualization vs Containerization

Virtualization: Hypervisor partitions physical server → multiple VMs, each with its own full OS. Heavy

Containerization: Containers share the host OS kernel, carrying only app + dependencies. Lightweight

📊 Comparison Table

FeatureVirtual MachinesContainers
OSFull guest OS per VMShare host kernel
Startup TimeMinutesSeconds
Resource UsageHigh (GBs of RAM)Low (MBs)
IsolationStrong (hypervisor-level)Process-level (namespaces)
PortabilityLimitedExcellent (runs anywhere)
Density per Host~10-20 VMs~100s of containers

🏢 Real-World Analogy

Virtualization = Apartment Building: Each VM is a separate apartment with its own utilities, kitchen, bathroom (full OS).

Containerization = PG/Hostel: You share the building (host OS kernel), only bring what you need. Don't manage electricity or maintenance.

⚠️ Drawbacks of Virtualization (led to containers)

  • Heavy resource overhead (each VM runs full OS)
  • Slow boot time & poor agility
  • Inefficient scalability
  • Limited application portability
  • Higher management complexity & infrastructure cost

🔒 Namespaces & cgroups — The Core of Containers

Golden Rule: "Namespaces isolate, cgroups control."

🧩 Linux Namespaces (Isolation)

NamespaceWhat It IsolatesExample
PIDProcess treeContainer sees its own PID 1; can't see host processes
NetworkIP addresses, portsMultiple Nginx containers all use port 80 internally
MountFilesystem viewFile changes inside container don't affect host
UTSHostnameEach container can have its own hostname
UserUser/group IDsMap container root → non-root user on host (security)

🚂 Analogy: Namespaces are like separate cabins in a train — same engine (kernel), different passengers, no visibility between cabins.

🎛️ Control Groups / cgroups (Resource Limits)

cgroups limit, control, and monitor resource usage:

  • CPU: Limit usage, assign CPU shares
  • Memory: Set max memory; container is killed if limit exceeded
  • Disk I/O: Limit read/write speeds
  • Network: Indirectly through traffic shaping

⚡ Analogy: cgroups are like electricity meters in apartments — each flat has a limit; one tenant cannot use all power.

📝 Task Solutions (from slides)

Task 1: Faulty container crashes host (high memory)▼

Q: Which container feature was misconfigured or missing?
→ cgroups (resource limits) were not set.

Q: Which kernel mechanism should have prevented this?
→ cgroups — specifically memory limits.

Q: Would namespaces alone solve this?
→ No. Namespaces only isolate (visibility), they don't limit resource consumption.

Task 2: Three containers — CPU hog, web server, DB▼

Q: Which Linux feature prevents Container A from consuming all CPU?
→ cgroups (CPU limits)

Q: Which feature ensures Container B cannot see processes of Container C?
→ PID Namespace

Q: Which namespace allows all three to use port 80 internally?
→ Network Namespace (each container gets its own network stack)

📦 Container Images & Registries

A container image is a read-only blueprint containing: Base OS (minimal) + App code + Libraries + Runtime + Config. Images are immutable.

🧅 Image Layers

Each instruction in a Dockerfile = one layer. Layers are immutable, cached, and reused across images.

Base OS Layer → Runtime Layer → Dependencies Layer → Application Code Layer (stacked bottom to top)

✅ Benefits: Faster builds (cache), smaller storage (shared layers), faster deployment (only missing layers downloaded).

🏪 Image Registries

A registry is a centralized repository to store, version, and distribute images. In DevOps: Registry = Bridge between CI and CD.

FeaturePublic RegistryPrivate Registry
AccessOpenRestricted (auth required)
SecurityLowerHigh
CostMostly freePaid
ExamplesDocker HubAWS ECR, Azure ACR, GHCR
Use CaseLearning, open sourceEnterprise, production

Image Naming: <registry>/<namespace>/<image>:<tag>

Example: docker.io/harpreet/webapp:v1

Common Tags: latest v1, v2 dev qa prod

⚙️ Docker Architecture

  • Docker Client: CLI (docker) that sends commands
  • Docker Daemon (dockerd): Background service managing images, containers, networks, volumes
  • Docker Images: Read-only templates
  • Containers: Runnable instances of images
  • Docker Registry: Stores & distributes images (Docker Hub)

🔄 Docker Lifecycle: Build → Ship → Run

Build Create an image (Dockerfile + docker build)

Ship Share via registry (docker push/pull)

Run Start containers (docker run)

Container States: Created → Running → Paused → Stopped

⚡ Why Docker is Faster than VMs

  • Containers share the Host OS Kernel
  • No Guest OS boot needed
  • Less resource usage & near-instant startup

🌍 Environment Variables in Docker

Environment variables are key-value pairs used to configure containers dynamically without changing the image.

💡 Ways to Pass Environment Variables

# Single variable docker run -e MY_VAR=value httpd env # Multiple variables docker run -e APP_ENV=production -e APP_VERSION=1.0 nginx # MySQL example (REQUIRED variables) docker run -d \ -e MYSQL_ROOT_PASSWORD=root123 \ -e MYSQL_DATABASE=college \ -e MYSQL_USER=admin \ -e MYSQL_PASSWORD=admin123 \ mysql:8
# Pass from host system export APP_PORT=8080 # Linux/Mac # or: $env:APP_PORT=8080 # PowerShell docker run -e APP_PORT=$APP_PORT nginx env # Using --env-file (clean & professional) # Create .env file: # DB_HOST=localhost # DB_USER=root # DB_PASS=secret docker run --env-file .env myapp

🔌 Port Mapping (-p)

-p maps a host port to a container port. Without it, containers are isolated and apps inside them are NOT accessible from the browser.

docker run -p <HOST_PORT>:<CONTAINER_PORT> IMAGE

Flow: Browser → localhost:8080 → Docker Host → Container:80 → Nginx

# Without -p (NOT accessible from browser) docker run nginx # With -p (accessible at localhost:8080) docker run -p 8080:80 nginx # MySQL example docker run -d -p 3307:3306 --name mysql-test -e MYSQL_ROOT_PASSWORD=root123 mysql

💾 Volumes & Bind Mounts

Volumes: Managed by Docker, stored in /var/lib/docker/volumes/. Persistent data

Bind Mounts: Mount any host directory into container. Great for development

📦 Volume Commands

docker volume create mydata # create volume docker volume ls # list volumes docker volume inspect mydata # inspect volume docker run -d -v mydata:/app/data --name mycont ubuntu docker volume rm mydata # remove volume docker volume prune # remove unused volumes

🔗 Bind Mount Example

# Mount current directory's html folder to nginx docker run -d \ -v $(pwd)/html:/usr/share/nginx/html \ -p 8080:80 \ nginx

🌐 Docker Networking

Docker provides network drivers to control container communication.

🔹 Bridge Network (Default)

  • Default for standalone containers on single host
  • Containers on same bridge communicate via IP
docker network ls docker network inspect bridge docker network create my_bridge_net docker run -d --name c1 --network my_bridge_net nginx docker run -d --name c2 --network my_bridge_net alpine sleep 300

🔹 Host Network

Container shares host's networking stack — no separate IP, faster performance. Linux only.

docker run -d --network host nginx curl http://localhost

🔹 Overlay Network

Used in Docker Swarm to connect containers across multiple hosts.

docker swarm init docker network create -d overlay my_overlay docker service create --name web --network my_overlay -p 8080:80 nginx

🔹 Built-in DNS

Containers on user-defined bridge networks can resolve each other by container name.

docker network create app_net docker run -d --name backend --network app_net nginx docker run -it --name client --network app_net alpine sh ping backend # ← resolves by container name!

🐳 Dockerfile & Image Building

A Dockerfile is a script of instructions to build a container image. Each instruction = one layer.

📄 Example: Custom Nginx Image

# Dockerfile FROM nginx:alpine COPY index.html /usr/share/nginx/html/index.html COPY default.conf /etc/nginx/conf.d/default.conf EXPOSE 80
# Build & Run docker build -t custom-nginx:v1 . docker run -d -p 8080:80 --name nginx-container custom-nginx:v1 # Visit http://localhost:8080

📄 Example: Node.js App

# Dockerfile FROM node:18-alpine WORKDIR /app COPY package.json . RUN npm install COPY app.js . EXPOSE 3000 CMD ["node", "app.js"]
docker build -t node-demo:v1 . docker run -d -p 3000:3000 --name node-container node-demo:v1 # Visit http://localhost:3000 → "Docker Node App Running!"
